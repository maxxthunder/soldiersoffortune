# Soldiers of Fortune (USA) — reverse engineering

**[Password generator →](https://maxxthunder.github.io/soldiersoffortune/)** Build or decode SNES and Genesis passwords in your browser.

Soldiers of Fortune is the US release of The Bitmap Brothers' *The Chaos Engine*. This repo
holds disassemblies of the SNES and Genesis versions and tools for their password systems.
The two versions' passwords store the same data but use different encodings.

## Layout

| Path | Contents |
|------|----------|
| `disasm/snes/` | 65816 listings of the SNES ROM, one file per 64 KB bank (`bank_C0.asm` … `bank_D7.asm`), generated by `tools/disasm.py` |
| `disasm/genesis/` | 68000 listings of the Genesis ROM, one file per 64 KB (`rom_00.asm` … `rom_17.asm`), generated by `tools/disasm68k.py` |
| `disasm/names.txt` | Names for routines, tables and RAM variables, shared by both disassemblers and reassemblers |
| `docs/sof_password.md` | Password format for both versions: routine addresses, bit layout, checksums |
| `docs/ram_map.md` | What the known RAM variables hold, for both versions |
| `tools/disasm.py` | Disassembler: traces code from the reset/interrupt vectors, tracking register widths across calls and following jump tables |
| `tools/reasm.py` | Reassembles `disasm/snes/` and checks the result is byte-identical to the ROM |
| `tools/disasm68k.py` | Genesis disassembler: traces code from the vector table, then from pointers it can vet (long and word-offset jump tables, `MOVE.L #addr`, code after an `RTS`) |
| `tools/reasm68k.py` | Reassembles `disasm/genesis/` and checks the result is byte-identical to the ROM |
| `tools/check_68k.py` | Round-trips every 68000 opcode word through the disassembler and reassembler |
| `tools/sof_password.py` | Password decoder/encoder for SNES and Genesis |
| `tools/sof_password_generator.html` | The same in a web page: build a password for any party, or decode one |
| `tools/check_generator.py` | Checks the web page's JavaScript against `sof_password.py` |
| `tools/names.py` | Loads `disasm/names.txt` |
| `.github/workflows/checks.yml` | CI: runs the checks that don't need the ROMs, then copies the generator page to the `gh-pages` branch |
| `tools/sof_genesis_romcheck.py` | Checks `sof_password.py` against the Genesis ROM's own password code, run in an emulator |

## You need

- **The ROMs, which are not included.** Put them in the repo root as
  `Soldiers of Fortune (USA).sfc` (SNES) and `Soldiers of Fortune (USA).md` (Genesis).
  `.gitignore` keeps them out of commits.
- Python 3.8 or newer.
- Optional: Node.js for `check_generator.py`, and `pip install unicorn` for `sof_genesis_romcheck.py`.

## Usage

Decode passwords (with no arguments, it runs its self-test):

```bash
python tools/sof_password.py W1V19S2SH21Q
python tools/sof_password.py --genesis 9NB5JM115GQ#
```

To make a password, use the [online generator](https://maxxthunder.github.io/soldiersoffortune/),
or open `tools/sof_password_generator.html` in a browser, which works offline.

Regenerate the disassembly and confirm it rebuilds the exact ROM:

```bash
python tools/disasm.py "Soldiers of Fortune (USA).sfc" disasm/snes
python tools/reasm.py disasm/snes "Soldiers of Fortune (USA).sfc"
python tools/disasm68k.py "Soldiers of Fortune (USA).md" disasm/genesis
python tools/reasm68k.py disasm/genesis "Soldiers of Fortune (USA).md"
```

Run the cross-checks:

```bash
python tools/check_generator.py
python tools/sof_genesis_romcheck.py
python tools/check_68k.py
```

## Reading the listings

Routines and tables named in `disasm/names.txt` appear under those names instead of `L_xxxxxx`,
both as labels and in operands, and the reassemblers turn them back into addresses. A line that
touches a named RAM variable shows its name at the end of the comment. To name something, add a
line to `names.txt` and regenerate the listing.

Each instruction line shows its address, its raw bytes and the register widths in effect:
`m`/`x` mean 8-bit A/index registers, and `M`/`X` mean 16-bit. Bytes the tracer never
reached are shown as `db` and may be code or data. About 4.5% of the ROM is traced as
code (31,767 instructions, up from 3.1% when tracing only from the vectors). The extra
entry points come from pointers: `LDA #lo`/`STA a`, `LDA #bank`/`STA a+2` pairs (the object
script pointers that `JML [$46]` runs), `PEA` bank/address pairs, and the bytes after each
`RTS`/`RTL`/`JMP`. A guess is kept only if every path from it decodes without opcodes that the
vector-reached code never uses (`guesses()` and `plausible()` in `tools/disasm.py`). The rest
of the ROM is mostly graphics and compressed data. To trace more of it, add
`(address, m, x)` to `EXTRA_ENTRIES`.

All 11 controller reads in the ROM (`$4218`–`$421B`) are now traced, and none of them
checks for a cheat. The menus read through `$CD014C` (`$4C`/`$4E` held, `$50`/`$52` new;
the new-press bytes are never read). In game, `$C0B16D` reads into `$94`–`$9A`. The main
loop copies those to `$06F3`/`$06FB`/`$06FD`, where they drive player control, item
cycling (`$C20E11`) and pause on Start (`$C20831`). The other reads are "press any
button" waits and the `$D108DB` list menu. There are no button-sequence tables or held
combos, and no writes to the level, lives or money variables depend on input.

Genesis lines show the address and the raw words. Unreached bytes are `dc.b`. The vector table and
the jump tables the tracer followed are shown as `dc.l` (pointers) and `dc.w` (offsets, with their
targets in the comment). The Z80 sound driver, `$14D044`–`$14E262`, is marked as a region; the
68000 copies it into Z80 RAM at start-up (`z80_load_driver`). The code sits
in `$000000`–`$01EB2E`, and about 55% of that is traced (4.4% of the ROM); the rest of that range
is mostly tables. Above it the ROM is graphics and level data. Guessed entry points must decode cleanly along every
path and avoid instructions only data turns into (`rare()` in `tools/disasm68k.py`); add
addresses to its `EXTRA_ENTRIES` to trace more.
